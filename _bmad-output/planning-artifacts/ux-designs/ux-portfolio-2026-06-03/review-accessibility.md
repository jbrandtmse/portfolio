# Accessibility Review — portfolio

*Reviewer: accessibility specialist. Target: WCAG 2.1 AA (the project's stated floor per NFR-2), plus the spec's named a11y commitments. Scope: the UX spine pair (`EXPERIENCE.md` / `DESIGN.md`), the decision log, `source-extraction.md` (NFR-2), and a sampling of the `.working/*.html` mocks with their a11y annotation panels. Critique only — the spines were not modified. Contrast ratios below were computed from the locked hex tokens in `DESIGN.md` using the WCAG relative-luminance formula.*

## Overall verdict

**Adequate, with sharp gaps.** The accessibility *thinking* in this pair is genuinely strong — the two-layer reduced-motion gate, the non-modal Guide contract (`role="dialog"` + `aria-modal="false"` + `role="log"`/`aria-live` batched-per-message), the "color is never the sole signal" discipline, the crawlable Mirror fallback, and the headline contrast figures are all correct and well-reasoned, and the canonical mocks largely render them faithfully. But three things keep it from "strong": (1) the **Invite-Me form — a primary conversion surface (UJ-2 climax, FR-31) — has no accessible markup or validation/error spec anywhere**; (2) a cluster of **muted/ghost ink colors fail AA for normal text** (`#9A8E79`, `#8A8273` at ~2.8–3.6:1) while carrying real state-bearing copy; and (3) the **non-modal focus model is under-specified on the return path** (focus-on-minimize, focus-after-citation-route), which is exactly where a non-trapped dialog goes wrong. None are unfixable, but a downstream dev handed this spine today could ship all three wrong while believing they were compliant.

## Findings

### Critical

- **[critical] The Invite-Me form has zero accessible specification — no markup, no field list, no labels, no validation pattern, no error states, no success announcement.** (Location: EXPERIENCE.md State Patterns / Component Patterns — there is no Invite-Me form component; the Speaker Surface and Close only carry a CTA `<a href="/invite">`; no `.working/*.html` mock contains a single `<form>`, `<input>`, `<label>`, `<select>`, or `<textarea>`.) FR-31 explicitly requires the form be "keyboard-operable, labeled, accessibly validated" and capture a structured attribution field, and UJ-2's climax *is* submitting it. The spine names the confirmation copy ("I reply within [N] business days") but nothing about the input layer. A dev will invent field semantics, and accessible client-side validation (programmatic label association, `aria-invalid`, `aria-describedby`/`aria-errormessage` error wiring, error summary + focus management on submit, required-field indication beyond color, a `role="status"`/`role="alert"` success announcement) is precisely what gets skipped when unspecified. *Fix:* add an Invite-Me form component to EXPERIENCE.md State + Component Patterns specifying: every field has a persistent visible `<label>` (not placeholder-as-label); required fields marked in text (not asterisk/color alone); inline errors associated via `aria-describedby` with `aria-invalid="true"`; an error summary that receives focus on failed submit; the attribution field as a labeled `<select>` or radio group; and the receipt confirmation announced via a polite live region. Mock at least one state (resting + error + submitted) so the contract is concrete.

### High

- **[high] Ghost / "still to come" text fails AA contrast while carrying meaningful state.** (Location: DESIGN.md `artifact-card.ghost-variant` "muted ink (#9A8E79)"; `era-band.span` "italic 11.5px in #9A8E79"; rendered in `mock-glassbox-index.html` ghost cards — "Architecture", "Epics & stories", "Retrospectives", "As it accrues" — and the timeline era spans.) `#9A8E79` is **2.84:1 on `surface-base`** and **3.01:1 on `surface-raised`** — both below the 4.5:1 AA floor for normal text. This directly undercuts the spine's own promise that "status is always also stated in text" (DESIGN.md Colors): the upcoming-node text *is* the non-color signal, but low-vision users can't read it. The italic 11.5px era span is the worst case (small + italic + 2.84:1). *Fix:* darken the ghost/upcoming ink to at least 4.5:1 on both surfaces (≈`#7A6E58` or darker on cream); keep the dashed border + "As it accrues" wording for the visual "muted" read, but don't let the *text* itself drop below AA. If "ghosted = lower contrast" is an intentional affordance, it cannot apply to text that conveys state.

- **[high] Metric source-attribution line fails AA contrast.** (Location: DESIGN.md `metric.source` "italic 11.5px in #8A8273"; the credibility strip in `mock-speaking.html`.) `#8A8273` is **3.36:1 on base / 3.56:1 on raised** — below 4.5:1 for normal text. The source line is load-bearing: it's the receipt that makes the audience-draw figure credible (the whole "skeptic gets the receipts" thesis). Same defect class as the era-span color. *Fix:* raise the source-line ink to ≥4.5:1 (e.g. reuse `ink-secondary #6B5D4A`, which is 5.63:1 and already the spine's sanctioned small-meta color), or enlarge to ≥18px/700 to qualify for the 3:1 large-text threshold. The latter fights the "quiet source" intent, so recoloring is cleaner.

- **[high] The non-modal Guide focus model is incomplete on the return path — focus-on-minimize and focus-after-citation-route are unspecified.** (Location: EXPERIENCE.md Accessibility Floor + Component Patterns + Interaction Primitives; the agent mock states "focus moves in but is not trapped" and "Esc minimizes" but is silent on where focus goes afterward.) For a *non-modal* dialog the return path is the hard part and the spec stops exactly there. Two unaddressed cases: (a) **on minimize (Esc or the minimize button), where does focus go?** If it stays on the now-hidden panel it is orphaned and the keyboard user is stranded mid-page; it must move to the pill (the invoking control). (b) **When a citation routes the page behind** (the signature cite→route loop), focus is in the floating panel but the meaningful content change happens in the document behind it — a screen-reader user gets no signal the page navigated and no clear way to move focus to the new content. *Fix:* specify in the Accessibility Floor: on minimize/close, return focus to the Guide pill; on citation activation, define focus behavior explicitly (e.g. keep focus in the panel and announce the route change via a polite live region, OR offer an affordance to move focus to the routed content) — and confirm the panel is reachable in DOM/tab order *after* the pill so a keyboard user can tab into it without a trap, and back out to the page.

- **[high] Reduced-motion is specified globally but not pinned per animated surface, and the only mock that demonstrates it is the hero.** (Location: EXPERIENCE.md State Patterns "Reduced-motion" + Accessibility Floor two-layer gate; no `prefers-reduced-motion` media query appears in *any* `.working/*.html` mock — only an annotation in `mock-hero-final.html`.) The global statement is good ("no GSAP/ScrollTrigger/WebGL init; halos/sweeps render static; instant section changes") but the task's named surfaces aren't individually covered: the **scene-rail progress-meter fill** (an animated width), the **Guide thinking "progress sweep"** (the agent mock calls it "a single soft motion-hint"), and the **S2 cinematic/scene-rail "directed camera path"** are not each tied to an explicit static fallback, and the Lenis/smooth-scroll decision is left as "avoid... or gate it." A dev reading per-component sections won't see the gate. *Fix:* in each animated component's spec (scene-rail, Guide thinking-state, timeline live halo — already static, the S2 canvas), add an explicit "under `prefers-reduced-motion`: [static treatment]" line, and state the meter renders as a static filled bar and the thinking sweep as static text. Confirm both layers (CSS media query AND the JS init-guard) are required, not either/or.

- **[high] The S2 "directed camera path" is committed scroll-jacking; the visible-skip-during-scroll-jack requirement (FR-2) is implied but not pinned to it.** (Location: EXPERIENCE.md Interaction Primitives "Banned: scroll-jacking without a visible skip affordance"; Stage sequencing FR-3.) The anti-pattern is named and the scene-rail is called "the antidote," but the spec never states the hard rule that *while the camera path is driving scroll, the skip/progress affordance must remain visible and operable*, nor that the camera path must be fully disabled under reduced-motion (it says "degrades to instant section changes," which is the visual fallback, not explicitly a motion-sickness guard). Scroll-hijacking is a known WCAG 2.1 pain point (2.2.2 Pause/Stop/Hide-adjacent, plus vestibular harm). *Fix:* state explicitly that the scene-rail skip + per-scene jump stay visible and keyboard-operable throughout any directed-camera sequence, and that the camera path is one of the things the reduced-motion JS gate disables outright (not merely speeds up).

### Medium

- **[medium] The scene-rail promises "jump-to-scene" but only ships two jump affordances — the 7 scene ticks are non-interactive text.** (Location: EXPERIENCE.md Interaction Primitives line "the persistent scene-rail provides progress, jump-to-scene, and the FR-2 Skip" + Deep-linking "every Scene is reachable via a stable in-page anchor"; vs Component Patterns line 118 and `mock-hero-final.html` where the rail is a `<ul>` of plain `<li>` text — only "Skip to the end" and "Jump: book a talk" are real `<a>`s.) There's an internal contradiction: the primitives claim per-scene jump, the component + mock deliver only skip-to-end and jump-to-speaking. A keyboard or screen-reader user cannot jump from the rail to Scene 3/5/6. The scene names are also `<li>` text with the *ticks* `aria-hidden` — fine for "color isn't the only signal," but it means the rail is announced as a 7-item list with no actionable targets beyond the two anchors. *Fix:* decide and pin it: either make each scene tick a real in-page anchor `<a href="#thesis">` etc. (satisfying the "jump-to-scene" + deep-link promise and giving the rail real keyboard utility), or correct the primitives/Deep-linking text to say the rail offers progress + skip-to-end + jump-to-speaking only, with per-scene deep links living elsewhere (e.g. the fallback footer). As written, a dev can't tell which is the contract.

- **[medium] Resting input border (`#D8CAB3` hairline) fails WCAG 1.4.11 (3:1) for the control boundary; only the focus state passes.** (Location: DESIGN.md `input` "border: 1px solid {colors.border-hairline}" on `surface-base`; the Guide composer and the unspecced Invite-Me fields.) The hairline is **1.42:1** against the field/page — below the 3:1 needed for the visible boundary of an active UI component where the border is the sole delimiter. The focus state brings a navy border (10.15:1, passes), so the issue is purely the *unfocused* field being hard to locate for low-vision users. (Note: purely *decorative* card/divider hairlines are exempt under 1.4.11; this finding is specifically about form-control boundaries.) *Fix:* give inputs (and any control whose only boundary is the hairline) a resting border that meets 3:1 — e.g. a slightly darker border token for controls, or pair the hairline with a fill/contrast cue. The button-secondary "quiet variant" (1px hairline) has the same exposure if used as a standalone control; the hero fork's outlined buttons are fine (they use `ink-primary` 15:1 / `accent` 10:1 borders).

- **[medium] The "Copied ✓" announcement pattern is fragile as drafted, and the resting→copied state-change announcement isn't specified.** (Location: EXPERIENCE.md State Patterns "Copy default / Copied"; `mock-speaking.html` puts `aria-live="polite"` directly on the copy `<button>` whose label is permanently "Copied ✓" in the static state.) `aria-live` on the button itself only announces if *that node's* content mutates while it stays in the DOM, and the spine doesn't say whether the announcement is the button's own label change or a separate live region. A dev could ship a button that flips to "Copied ✓" with no reliable SR announcement, or one that announces stale. *Fix:* specify a dedicated visually-hidden `role="status"` (polite) region that announces "Bio copied to clipboard" on success, distinct from the visual button-label swap; and note the button's accessible name should not get permanently stuck at "Copied" (it should revert with the visual state, per the "reverts after a beat" intent).

- **[medium] Reel/video accessibility is partly specified but captions/transcript are unaddressed.** (Location: EXPERIENCE.md Component Patterns "Reel" + DESIGN.md `reel-poster`.) The poster path is handled well — real poster, `aria-label` naming the reel + 90s duration, **no autoplay**, static link fallback to YouTube/`/speaking/reel` (the mock confirms all of this). But the spec never states the **captions/transcript expectation** for the reel or the full talk videos. WCAG 1.2.2 (captions) and 1.2.x apply once the video plays, and an embedded YouTube player's caption availability depends on the uploaded asset. Audio-off-by-default is covered for the soundtrack (FR-30) and there's no autoplay-with-sound, so that commitment is met. *Fix:* add a one-line expectation that the reel and talk recordings ship with synchronized captions and that a text transcript/abstract is reachable (the Mirror already gives talk abstracts as HTML — state that this is the transcript-equivalent path, and that the hosted player must have captions enabled).

- **[medium] The "Still to come" divider in the Glass Box is `aria-hidden` inside the `<ol>`, so the upcoming-group framing is sight-only.** (Location: `mock-glassbox-index.html` `<li class="upcoming-label" aria-hidden="true">Still to come</li>`.) Sighted users get a clear "these next three are future" grouping; SR users get only each ghost card's own text. The ghost cards *do* each carry "As it accrues" + a future-tense note ("The technical design, once it's drawn"), so the meaning isn't entirely lost — but the explicit grouping cue is. This is a borderline call. *Fix:* either expose the "Still to come" label to AT (un-hide it, or provide it as an accessible group label/heading for the upcoming nodes), or confirm in the spine that per-card future-tense text is the deliberate SR-equivalent so a dev doesn't "fix" it inconsistently.

### Low

- **[low] DESIGN.md states the navy reversed-out color is `surface-base` cream (10.15:1), but the mocks reverse white `#FFFFFF` on navy for the pill, "Copied," and "Live" pills.** (Location: DESIGN.md `guide-pill.color: #FFFFFF`, `artifact-card.live-pill #FFFFFF text`, vs `button-primary.color: {colors.surface-base}`.) Both pass AA comfortably (cream-on-navy 10.15:1, white-on-navy 11.50:1), so this is not a contrast failure — only a token-consistency note. A dev following "cream reversed out of navy" for buttons but the mocks' `#FFFFFF` for pills will produce two slightly different reversed-text colors. *Fix:* pick one reversed-text token site-wide (the spine's stated cream, or white) and apply it consistently; purely cosmetic for a11y.

- **[low] Faint runway-tick dot ring (`#C0B49B`, 1.81:1) and the drafting grid (`#ECE3D3`, 1.12:1) are below 3:1 — acceptable only because they're decorative.** (Location: DESIGN.md `timeline-dot.faint`, `grid-line`.) Both are explicitly `aria-hidden`/decorative and no information depends on them (the timeline reading order + era labels + dates carry meaning in the `<ol>`), so 1.4.11 doesn't apply. Flagged only so a dev doesn't later attach meaning (a count, a state) to a faint tick without re-checking contrast. *Fix:* none required; keep the "no info lives only in the grid/ticks" rule enforced if these ever gain semantics.

- **[low] Heading hierarchy is clean in the real surfaces, but the mocks' review-scaffold `<h1>`s could mislead a copy-paste dev.** (Location: every `.working/mock-*.html` opens with a review-intro `<h1>` describing the surface, then the surface's own `<h1>`, producing 2 `<h1>`s per file.) The spine's rule is correct ("one page `<h1>`; section rules/reader notes are non-heading asides") and the *surface* markup honors it (e.g. glassbox: one `<h1>` + `<h3>` cards; timeline: one `<h1>` + `aria-label`'d era `<li>`s). The double-`<h1>` is purely a mock-annotation artifact. *Fix:* none needed for the spec; just ensure the build doesn't carry the review-intro headings into production.

## What's solid

Credit where due — the a11y foundation here is above the bar for a portfolio:

- **The Guide's core ARIA contract is correct and rare-to-get-right:** `role="dialog"` with `aria-modal="false"`, focus moved-in-but-not-trapped, transcript as `role="log"` + `aria-live="polite"` **batched per message (never per token)**, the thinking state announced once per message via `role="status"`, Esc-to-minimize preserving the thread, and all controls as real `<button>`/`<a>` with a visible `:focus-visible` ring. The "never per token" decision (reconciling the wow-thinking-surface with NFR-2) is exactly right and is honored in the mock.
- **Headline contrast is genuinely strong:** ink-primary 15.04:1, accent navy 10.15:1 (and the same reversed out), accent-hover 12.60:1, and — importantly — **ink-secondary passes AA for normal text at 5.63:1**, so the entire meta/caption/kicker tier isn't a contrast compromise. Focus rings (navy, 10.15:1) and the citation route-label mono (5.63:1) also pass.
- **"Color is never the sole signal" is applied consistently:** `aria-current` + weight + "Scene N of 7" text for the rail; "Live · in progress" pill text + a *static* (no-animation) halo for live state; ghosted upcoming nodes carry text status; audience level / ratings / placeholder flags all stated in text. The live-halo-but-no-animation choice is a thoughtful reduced-motion-friendly default.
- **Decorative-vs-meaningful is disciplined:** WebGL canvas `aria-hidden` with DOM equivalents, drafting grid and scene-rail ticks and timeline Dots/spine all decorative with text/links carrying meaning, the portrait placeholder carries a labeled `role="img"` with a real-`alt` commitment for the headshot.
- **The static / crawlable fallback is first-class, not bolted on:** the Mirror routes + `/browse` + the always-present footer reach 100% of agent-reachable content; the Master Timeline is one semantic `<ol>` reflowed by orientation (DOM order preserved); talk abstracts use native `<details>`/`<summary>` (works JS-off, text in DOM); the Glass Box index degrades to a plain `<ol>`; bios are selectable plain text behind the copy button. The "nothing hidden behind the magic" promise is structurally real.
- **Media defaults are safe:** no autoplay, no autoplay-with-sound, soundtrack off-by-default and user-controllable (FR-30), reel poster links out if the player fails, and the poster `<a>` is labeled with the reel name + duration.
