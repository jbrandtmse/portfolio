# Spine Pair Review — portfolio

## Overall verdict

This is a strong, unusually disciplined spine pair: a consumer can source-extract cleanly, every genuine `{path.to.token}` reference resolves, every named component carries both a visual and a behavioral spec, and every FR/UJ from the source extraction lands somewhere traceable. The single mechanical defect is that the `sources:` frontmatter in both files is not strict-YAML-parseable (`{planning_artifacts}/...` values read as flow-mappings) — but this is inherited verbatim from the canonical example spines, so it is a convention the toolchain is expected to tolerate rather than a project regression. The only substantive contract risks are soft ones: a known PRD↔spine positioning divergence carried as an explicit upstream-sync flag, and a Stage-1 scope ambiguity (Wings/Creative Lab) that touches UJ-3's primary beat.

## 1. Flow coverage — strong

Every named source journey (UJ-1 Devon, UJ-2 Mara, UJ-3 Sam) has a Key Flow with a named protagonist, numbered steps, an explicit `**Climax:**` beat, and a degraded/failure path (`*Degraded (...)*`). UJ-4 (Josh's maintenance flow) is correctly identified as a non-visitor flow and routed to Stage sequencing + Proof-as-Process rather than forced into Key Flows. Every Stage-1 FR from `source-extraction.md` maps to an IA surface, a Component Pattern, a State Pattern, or the Stage-sequencing table.

### Findings
- **medium** UJ-3 (Sam) step 1 depends on "creative content," but the extraction (`source-extraction.md` §journeys, UJ-3) and the Stage table both place Creative Lab / playables in Stage 2; Stage-1 fallback is only "curated creative links/embeds." The flow's climax ("a genuinely enjoyable moment — a playable embed or a track") is therefore a Stage-2 beat, while the surface map (`EXPERIENCE.md` IA) ships no creative surface in Stage 1. A consumer building Stage 1 has no home for UJ-3's payoff. (`EXPERIENCE.md` → Key Flows UJ-3 vs. Stage sequencing vs. IA route map.) *Fix:* state in UJ-3 which Stage-1 surface carries the wander beat (e.g. curated embeds on the Close/Thesis scene), or label UJ-3 explicitly as a Stage-2-complete journey with a thinner Stage-1 cut.
- **low** UJ-2's climax cites "I reply within [N] business days" with N unresolved (`[TBD]`/`[OPEN]`). Tracked in Open gaps, so not a coverage miss — but it sits inside a primary-conversion climax beat, so flag it as content-blocking for that flow's final step. (`EXPERIENCE.md` → Key Flows UJ-2 step 4; Open gaps.) *Fix:* none required pre-content; ensure the copy string is parameterized so the flow doesn't ship with a literal `[N]`.

## 2. Token completeness — strong

All six token groups are present and populated: `colors` (8), `typography` (8 roles + base family), `rounded` (5), `spacing` (8px scale + 7 named), `elevation` (flat + one shadow), `components` (18). Every color token carries a hex. Of 51 unique `{...}` references in DESIGN.md prose and 7 in EXPERIENCE.md, the only non-resolving token is `{artifact}` — which is the `/glass-box/{artifact}` route-slug placeholder, not a design token (false positive). Contrast is stated per-token for every load-bearing combination (ink-primary 15.04:1, ink-secondary 5.63:1, accent 10.15:1 both directions, accent-hover 12.76:1 — all on `surface-base`, all AA-verified inline).

### Findings
- **low** Several non-tokenized hex values are introduced only in component prose/frontmatter and never named as tokens: `#C6B89E` (artifact-card hover border), `#9A8E79` (ghost/era muted ink), `#C0B49B` (faint timeline-dot ring), `#8A8273` (metric source), plus the reel-poster gradient stops (`#24456B`, `#16263F`, `#101D31`). These are legitimately one-off per the flat/hairline system, but a consumer cannot reference them by name and must hard-code. (`DESIGN.md` frontmatter `components.*` + Components prose.) *Fix:* acceptable as-is for a delta system; if any recur in build, promote to a named neutral/ink-faint token.

## 3. Component coverage — strong

All 18 frontmatter components have a DESIGN.md Components prose spec and a DESIGN frontmatter token block. Cross-checking the 15 entries in EXPERIENCE.md's Component Patterns table against DESIGN's 18: every behavioral component resolves to a visual spec, with deliberate naming bridges that hold. No component is one-word; behavioral rules are real (JS-off `<details>`, autosave thresholds, optimistic toggle, non-modal focus rules, etc.).

### Findings
- **low** Two EXPERIENCE Component Patterns rows are *composed from* DESIGN components rather than 1:1-named: **"The fork"** (Hero) has no `fork` token — it is built from `button-primary` + `button-secondary` + the inline Guide link; **"Artifact reader"** (`/glass-box/{artifact}`) has no `artifact-reader` token — its visual spec is the typography drop-cap/pull-quote block plus `artifact-card`. Both are resolvable by a careful reader and DESIGN's typography prose covers the reader devices, but neither bridge is stated, so a consumer must infer the composition. (`EXPERIENCE.md` → Component Patterns rows 1, 6; `DESIGN.md` → Typography + Components.) *Fix:* add a half-clause naming the underlying tokens ("The fork = two `{components.button-*}` + inline Guide link"; "Artifact reader — long-form type block, see DESIGN Typography drop-cap/pull-quote").
- **low** Three EXPERIENCE rows are behavioral-only with no matching DESIGN component token, by design: **Static fallback footer**, **Flagship node** (a behavior of `timeline-dot` clusters), **Artifact reader** (above). Static fallback footer is plain nav and arguably needs no visual token; Flagship node is correctly a state/composition of `timeline-dot`. No fix needed — noting so the absence reads as intentional, not a miss.

## 4. State coverage — strong

The State Patterns table plus Accessibility Floor plus the per-component behavioral rules cover the load-bearing surfaces. JS-off and reduced-motion each have a dedicated Global row; cold-load is covered ("Loading", FCP-first SSG); the Guide walks empty/thinking/answer/below-threshold/collapsed; focus and offline are addressed. Color-is-never-sole-signal is enforced repeatedly (status in text + weight + shape).

### Findings
- **medium** No surface specifies an **error/failure state for the Invite-Me form** (FR-31), which is the terminal step of the primary-conversion journey (UJ-2). State Patterns, Component Patterns, and the IA all describe the form's *success* path (persisted + emailed, stated response time) but never the submit-failure, validation-error, or network-down state. Accessibility Floor mentions "accessibly validated" in passing, but no treatment is specified. (`EXPERIENCE.md` → State Patterns; Component Patterns has no Invite-Me/form row at all.) *Fix:* add an Invite-Me form row to Component Patterns and a submit-error / validation-error / offline-submit row to State Patterns (the conversion path cannot silently fail).
- **low** The **Guide error/unavailable state** (LLM endpoint down, retrieval service error — distinct from the honest below-threshold "I don't have that documented" no-model-call path) is not specified. Offline is covered for content via the Mirror, but the live Guide backend failing mid-conversation has no stated treatment. (`EXPERIENCE.md` → State Patterns Guide rows; "The Guide — grounding" section.) *Fix:* add a one-line Guide-unavailable treatment (e.g. fall back to the starter-prompt routes / Mirror links with an in-voice apology).
- **low** **Focus-visible** is asserted globally in Accessibility Floor ("visible `:focus-visible` ring") but the State Patterns table has no per-surface focus row beyond the Guide; for a keyboard-and-crawler-first site this is thin relative to the JS-off/reduced-motion rigor. (`EXPERIENCE.md` → Accessibility Floor vs. State Patterns.) *Fix:* optional — the global assertion is probably sufficient given DESIGN specifies focus rings per interactive component.

## Mechanical notes

- **YAML parseability (both files).** `sources:` list items use unquoted `{planning_artifacts}/...` / `{output_folder}/...` values. A YAML value beginning with `{` parses as a flow-mapping, so `yaml.safe_load` raises `ParserError` on the frontmatter of **both** DESIGN.md (fails at line 6) and EXPERIENCE.md (same cause). Quoting the four `sources:` entries makes DESIGN.md parse cleanly (18 components, all groups intact) and would fix EXPERIENCE.md identically. **However:** the canonical example spines (`experience-example-mobile.md`, `experience-example-shadcn.md`) use the *exact same* unquoted pattern, so this is the established `{path-template}` convention the consumer toolchain is expected to resolve before parsing — a low/medium portability note, not a project regression. *Fix (if strict-YAML portability is wanted):* wrap the `{...}` source paths in quotes in both files (and, ideally, upstream in the example spines).
- **Token resolution (automated).** 51 unique `{...}` refs in DESIGN.md prose + 7 in EXPERIENCE.md all resolve to defined frontmatter tokens; the only non-match is the `/glass-box/{artifact}` route slug (not a token). Zero genuine dangling references.
- **Component matrix (automated).** 18 DESIGN frontmatter components = 18 DESIGN prose specs (Citation chip & link combined). 15 EXPERIENCE Component Patterns rows; 13 map 1:1 to a DESIGN token, 2 are intentional compositions ("The fork," "Artifact reader") covered by other tokens/prose. No component lacks a behavioral rule; none lacks a visual spec.
- **Mock existence.** All six spine-cited mocks exist in `.working/`. `mockups/` does not yet exist (promotion pending — expected, not scored). Eight uncited `.working/` mocks are exploration/process artifacts (backstage never-render set), so their orphan status is expected.
- **Severity tally. critical 0 · high 1 · medium 3 · low 14.** high: §7 positioning divergence (PRD anchor vs. spine, flagged for `/bmad-correct-course`). medium: §1 UJ-3 has no Stage-1 home for its climax beat; §4 Invite-Me form has no error/validation/offline state on the primary-conversion terminal step; §5 six mocks cited only at one global IA line, none at the section it illustrates.
