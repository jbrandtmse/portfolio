# SEO / GEO Review — portfolio

Reviewer: SEO / GEO (generative-engine optimization) gate. Scope: the UX spine pair (`EXPERIENCE.md`, `DESIGN.md`) plus `.decision-log.md`, against the project's discoverability contract — **NFR-3** ("if it matters for SEO/AI, it must be in the initial HTML"), **FR-35** (structured data), **FR-7/FR-8** (agent-as-router / static fallback), and the primary speaking goal (**SM-1 / SM-2** — organizers Google Josh, peers cite the site). Critique only; the spines were not modified. Severities are weighted by impact on the speaking-discoverability goal plus downstream build risk.

Verified against current (2026) sources where facts may have drifted: AI-crawler user-agent tokens and Google's FAQ-rich-result restriction (see Findings S-2 and S-6).

## Overall verdict

The two-layer IA (narrative `/` arc over a crawlable Static Mirror) is the **right architecture** for reconciling a cinematic, agent-first site with the "credible-when-Googled" mandate, and the spine is unusually disciplined about JS-off parity: talk abstracts in `<details>` with text in the DOM, bios as selectable text, timelines as real `<ol>`, the WebGL canvas `aria-hidden` with DOM equivalents. But the SEO/GEO **floor is asserted, not engineered** — the entire contract lives in one prose paragraph (`EXPERIENCE.md` *Responsive & Platform → SEO/GEO floor*), and the load-bearing mechanics are missing: no `/about` route for the `Person`/`ProfilePage` schema it names, **no crawlable FAQ/Q&A surface at all** (the Guide's Q&A is JS-gated chat), and **zero specification of canonical tags, sitemap, or robots/AI-crawler policy** — even though the two-layer model manufactures a duplicate-content problem (arc teaser vs. Mirror route) that only canonicalization resolves. Rating: **thin** — solid bones, but the surfaces and emission rules that turn NFR-3 from a promise into a verifiable artifact are under-specified, and two named schema types (FAQPage, Person/ProfilePage) point at surfaces that do not exist in the IA.

## Findings

### Critical

**C-1 · No crawlable Q&A / FAQ surface exists, yet FAQPage schema is promised — the GEO answerability path has no HTML to stand on.**
*Location:* `EXPERIENCE.md` → *Responsive & Platform → SEO/GEO floor* (names `FAQPage (Q&A)`); IA route map (§ *Stage-1 surface → route map*); *The Guide* sections. The route map has no `/faq`, no Q&A block on any Mirror route. The only Q&A on the site is the **Guide**, which is explicitly a JS-gated, non-modal chat overlay with **no URL of its own** ("site-wide overlay with no URL") and answers rendered client-side into a `role="log"`.
*Why it's critical:* This is the core GEO mechanism for the speaking goal. When an LLM (or Google's AI surfaces) is asked "who is Joshua R. Brandt / can he speak on X," it reads server-rendered HTML — not a chat widget it cannot operate. The spine routes *all* question-answering through the Guide, then names `FAQPage` schema with no page to attach it to. Result: the most citable content format (direct Q&A pairs) is absent from the crawlable surface, and the schema references a non-existent surface (it would be invalid/empty JSON-LD). The Guide's three starter prompts ("Is this site actually built with the BMAD Method?", "Can he deliver a conference talk?", "Show me something I haven't seen") are exactly the Q&A pairs that belong in HTML — they currently exist only as JS button labels.
*Fix:* Add a crawlable Q&A surface to the Stage-1 IA — either a dedicated `/faq` (or `/about#faq`) route, or a server-rendered FAQ block appended to `/speaking` and the home Mirror. Seed it with the same KB-grounded answers the Guide serves (the starter prompts are the natural seed set), as real `<h3>` question + `<p>` answer pairs. Attach `FAQPage` JSON-LD there. This makes the Guide a *progressive enhancement* over a crawlable Q&A base (true to FR-7's "agent = router, not the sole source of any fact") rather than the only Q&A path. Note (per 2026 verification): Google has restricted FAQ *rich snippets* to gov/health domains, so do not expect SERP enhancement — but `FAQPage` markup plus the plain-text Q&A remains high-value for LLM/answer-engine citation, which is the actual goal here.

**C-2 · Canonicalization and the arc-teaser vs. Mirror-route duplicate-content problem are unaddressed.**
*Location:* `EXPERIENCE.md` → *IA two-layer model* (every rich surface lives BOTH as a teaser Scene on `/` AND as a full Mirror route); SEO/GEO floor paragraph (silent on canonical). The decision log (*IA + navigation model*) likewise names no canonical policy. Searching both spines for `canonical` returns only the *name-string* sense ("canonical name string"), never the HTML `rel="canonical"` sense.
*Why it's critical:* The two-layer design **deliberately duplicates content** — Scene 4 on `/` teases `/speaking`, Scene 5 teases `/work/loandemo`, Scene 6 teases `/glass-box`. Teasers that lift abstract/case-study text create near-duplicate passages across `/` and the Mirror route. With no canonical strategy, search and AI engines may index the teaser on `/` (a JS-heavy cinematic page) instead of the clean Mirror route, splitting ranking signals and risking the *wrong* URL being cited to an organizer. The Mirror routes are supposed to be "clearly the canonical indexable surface" — but nothing in the spec *declares* them canonical.
*Fix:* Specify in `EXPERIENCE.md` that (a) each Mirror route is self-canonical (`<link rel="canonical">` to itself); (b) the home `/` teaser Scenes are explicitly *summaries that link out*, not full-text copies — keep teaser prose short and distinct from the Mirror's full text, so they are not near-duplicates; (c) the home page's load-bearing facts (the bio answer-snippet, see C-3) are canonicalized to `/` or `/about`. Add this as an explicit IA rule, not an implementation footnote.

### High

**H-1 · `Person` + `ProfilePage` schema is assigned to "home/about," but there is no `/about` route and `/` is the JS-heavy cinematic arc — the canonical identity facts have no clean home.**
*Location:* `EXPERIENCE.md` SEO/GEO floor ("`Person`+`ProfilePage` (home/about)"); IA route map lists only `/` (the Scene Arc), `/timeline`, `/speaking`, `/work/loandemo`, `/glass-box`, `/invite`, `/browse` — **no `/about`**. The full long bio lives in the Speaker Surface bio-copy block (`/speaking`), and the home `<h1>` is the positioning line, not a bio.
*Why it's high:* `ProfilePage` + `Person` is *the* schema an answer engine uses to build an entity card for "Joshua R. Brandt." Pointing it at `/` is risky: `/` is the cinematic, scene-railed, JS-rich page whose initial-HTML bio content is unspecified (the hero is a name + positioning line + headshot, not a bio paragraph). Pointing it at "/about" references a route that does not exist. Either way the authoritative `Person` description (the 100–150-word bio) is on `/speaking`, where it is schema-typed as part of an `Event`/speaker context, not as the site's primary `Person` entity.
*Fix:* Resolve the host surface explicitly. Either (a) add a Stage-1 `/about` Mirror route carrying the long bio, headshot with meaningful `alt`, name, and the `Person`+`ProfilePage` JSON-LD; or (b) commit that `/` server-renders the long bio in initial HTML (an "answer-first" intro paragraph, see H-2) and host `Person`/`ProfilePage` there. Whichever is chosen, the 100–150-word bio must be plain server-rendered text on the surface that owns the `Person` schema, and `sameAs` should list the channel URLs (YouTube/Suno/GitHub) once known — these are the entity-reconciliation signals AI engines rely on.

**H-2 · "Answer-first intros" and the brand-in-short-answer rule are asserted but never operationalized for any specific surface.**
*Location:* `EXPERIENCE.md` SEO/GEO floor ("answer-first intros, clean heading hierarchy, plain-text key facts"); the *Voice and Tone* / microcopy section governs tone but specifies no answer-first lede for `/`, `/speaking`, or `/work/loandemo`. The hero `<h1>` is "Seasoned, building at the frontier" — evocative, but it is **not** an extractable answer to "who is Joshua R. Brandt."
*Why it's high:* GEO answerability depends on a plain, self-contained, name-bearing sentence near the top of the key surfaces — the passage an LLM lifts verbatim as a citation. The brand string the spine fights for ("Joshua R. Brandt, MSE") appears in the wordmark and JSON-LD but is **not guaranteed in a body-text answer sentence**. "Restraint is the flex" and "no exclamation marks / state the bet, name the receipt" are good GEO instincts, but an evocative poster headline alone gives an answer engine nothing concrete to quote.
*Fix:* Mandate, per key Mirror surface, a first body paragraph that answers the surface's core question in plain text and names the entity — e.g. on `/` or `/about`: *"Joshua R. Brandt, MSE is a software engineer with 30 years of shipping experience, now working at the frontier of agentic engineering…"*; on `/speaking`: a one-sentence answer to "what does he speak on and can he deliver." This is a microcopy deliverable, not just a principle — add it to *Voice and Tone* as required strings (the copy-paste 50-word bio is a ready candidate for the `/` answer-lede, reused).

**H-3 · No sitemap.xml or robots.txt is specified, and the "don't block AI crawlers" requirement has no concrete allow-list.**
*Location:* `EXPERIENCE.md` SEO/GEO floor and `.decision-log.md` are silent on `sitemap.xml` and `robots.txt`. NFR-3 (per `source-extraction.md` and PRD) explicitly says "do not block AI crawlers," but the spine never translates that into an artifact. The site is a static Astro build (no CMS), so these files must be authored by hand or generated — they will not appear by default.
*Why it's high:* For a low-surface-count site whose entire goal is to be *found and cited*, a sitemap (listing every Mirror route + `lastmod`) and a permissive robots.txt are the cheapest, highest-leverage discoverability artifacts. "Don't block AI crawlers" is currently aspirational — without an explicit allow posture, a default or copied robots.txt could silently disallow the very bots (GPTBot, ClaudeBot, PerplexityBot, OAI-SearchBot) whose citations drive SM-2.
*Fix:* Specify in the spine (Responsive & Platform): (1) a generated `sitemap.xml` enumerating all Mirror routes; (2) a `robots.txt` that explicitly **Allows** the current AI-crawler tokens. Verified 2026 token names to allow: `GPTBot`, `OAI-SearchBot`, `ChatGPT-User` (OpenAI); `ClaudeBot`, `Claude-User`, `Claude-SearchBot` (Anthropic — note `anthropic-ai` is now legacy); `PerplexityBot`, `Perplexity-User`; `Google-Extended`; `Applebot-Extended`; `Amazonbot`; `CCBot`. Reference the sitemap from robots.txt. This is a build-config deliverable the spine should name so it is not forgotten.

**H-4 · The reel `VideoObject` cannot satisfy "in the initial HTML" as currently designed — required fields and the missing reel URL block it.**
*Location:* `EXPERIENCE.md` SEO/GEO floor (`VideoObject (talks + reel)`); *Component Patterns → Reel* ("no autoplay; the poster links out (YouTube / `/speaking/reel`) if the player can't load"); *Open gaps* (`[OPEN] READY 2026 talk details … and which talks fill the reel`; channel handles `[OPEN]`).
*Why it's high:* A valid, useful `VideoObject` requires `name`, `description`, `thumbnailUrl`, `uploadDate`, and a `contentUrl` or `embedUrl` — all in server-rendered HTML, independent of whether the player JS loads. The reel is the stated credibility engine for UJ-2 (Mara), and `/speaking/reel` appears as a fallback target but **is not a route in the IA map**. With the reel URL, upload date, and duration all `[OPEN]`, the schema will ship empty or invalid, and the most conversion-critical media object becomes non-indexable. (The reel poster is decorative gradient + grid — it carries zero text for a crawler if the JSON-LD is hollow.)
*Fix:* (a) Specify the `VideoObject` field set as a required initial-HTML emission (name/description/thumbnailUrl/uploadDate/duration/contentUrl|embedUrl), flagged to populate from the content-inventory `[OPEN]` items before launch — not deferred. (b) Add `/speaking/reel` (and per-talk recording URLs) to the IA route map, or remove it as a fallback target and point the poster at the canonical YouTube URL. (c) Ensure `duration` (~90s) and `uploadDate` are real values, not placeholders, at ship — a `VideoObject` with placeholder fields is worse than none.

### Medium

**M-1 · The Glass Box `CreativeWork`/`Article` schema and the artifact reader's structured data are unspecified.**
*Location:* `EXPERIENCE.md` SEO/GEO floor lists `CreativeWork (projects)` — scoped to the two flagship case studies (`/work/loandemo` and the portfolio-itself flagship). The *Glass Box* sections (`/glass-box`, `/glass-box/{artifact}`) are the day-one *remarkable* element and the UJ-1 climax, but **no schema is assigned to the artifact reader pages** at all.
*Why it's medium:* The Glass Box is the peer-share / SM-2 engine ("proof-as-process"). Each artifact reader (`/glass-box/{artifact}`) is long-form editorial content an AI engine would happily cite — but with no `Article`/`CreativeWork`/`TechArticle` typing, `datePublished`, or `author`, it is just untyped prose. The recursion story ("you're reading the build history of the site you're reading it on") is exactly the citable narrative GEO should amplify.
*Fix:* Assign `CreativeWork` (or `Article`/`TechArticle`) JSON-LD to each `/glass-box/{artifact}` reader, with `headline`, `datePublished`, `author` (Person → Joshua R. Brandt, MSE), and `isPartOf` the Glass Box collection; consider `CollectionPage` for the `/glass-box` index. Confirm the publish-allowlist (default-deny) also governs which artifacts emit schema, so backstage docs (decision logs, reviews) never leak structured data.

**M-2 · "Clean heading hierarchy" is asserted globally but the home Scene Arc is the likeliest place it breaks.**
*Location:* `EXPERIENCE.md` *Accessibility Floor* ("one page `<h1>`; section rules and reader notes are non-heading asides") and SEO/GEO floor ("clean heading hierarchy"). The home `/` stacks 7 Scenes (Hero/Thesis/Timeline/Speaker/Flagship/Glass Box/Close) on one page; each Scene is a major section.
*Why it's medium:* The home page is the highest-traffic, highest-stakes crawl surface and the one most likely to produce a broken outline: with one `<h1>` (the positioning line) and 7 sectional Scenes, each Scene needs a single coherent `<h2>` and teasers must not introduce stray `<h1>`s or skip levels. A muddy outline on `/` directly degrades how engines parse and snippet the page. The spine states the *rule* but doesn't map the Scene→heading-level structure.
*Fix:* In `EXPERIENCE.md`, pin the home-page outline explicitly: `<h1>` = positioning line (hero); each Scene = one `<h2>` with a meaningful heading (e.g. "Speaking," "The flagship: loandemo," "The Glass Box"); teaser sub-elements use `<h3>` or non-heading asides. Confirm Mirror routes each carry their own single `<h1>` (page title) — `DESIGN.md` typography already provisions `h1` for "Glass Box, Timeline, Speaking," which is consistent; just state the home-arc mapping.

**M-3 · The arc teaser's duplicate of abstract/case-study text is a GEO/duplication risk even with canonical set (see C-2), specifically for the speaker abstracts.**
*Location:* `EXPERIENCE.md` route map (Speaker = Scene 4 teaser on `/` + full at `/speaking`); *Talk card* (150–200-word abstracts; first expanded, rest in `<details>` with "text in the DOM for crawlers").
*Why it's medium:* The 150–200-word abstracts are prime citable text. If the home Scene-4 teaser reproduces an abstract and `/speaking` also carries it, two URLs compete for the same passage; an engine may surface the cinematic `/` over the clean `/speaking` for an organizer query. Canonical (C-2) mitigates ranking dilution but the cleaner GEO answer is to keep the abstract *full text on one surface only*.
*Fix:* State that full abstracts live **only** on `/speaking` (and `/work/loandemo` for the talk linkage); the home Scene-4 teaser carries a 1–2 sentence hook + a link, never the full abstract. Same rule for case-study body text (Glass Box / loandemo).

**M-4 · `Event` JSON-LD completeness and the "upcoming vs. past talk" distinction are unspecified — risk of invalid Event markup.**
*Location:* `EXPERIENCE.md` SEO/GEO floor (`Event (talks)`); decision log *Speaker Surface* ("Event + VideoObject"). Talk titles/abstracts are `[ASSUMPTION]`/seeded; READY 2026 date is `[OPEN]`.
*Why it's medium:* `Event` requires at minimum `name`, `startDate`, and a `location` (or `eventAttendanceMode`/virtual location). The signature talks on `/speaking` are described as *repeatable topics* (formats/durations offered) rather than scheduled instances — a `Course`/`CreativeWork`/`PresentationDigitalDocument` may model "a talk I can give" better than `Event`, which implies a dated occurrence. Emitting `Event` without a real `startDate`/`location` produces invalid markup; conflating "talks I offer" with "a scheduled talk" muddies the entity.
*Fix:* Distinguish in the spine: (a) *scheduled* appearances (e.g. READY 2026, once dated) → `Event` with `startDate` + `location`/virtual; (b) *offered signature topics* (the evergreen talk cards) → model as `CreativeWork`/`PresentationDigitalDocument` (or omit Event for these and rely on the FAQ/answer text). Don't emit `Event` for undated topics.

### Low

**L-1 · No Open Graph / Twitter (X) card metadata is specified — directly undercuts the peer-share (SM-2) goal.**
*Location:* Neither spine mentions `og:` or `twitter:` tags (confirmed by search). The whole reputation thesis (SM-2) is *peers share the link in Discord/X/Slack* (UJ-1 resolution).
*Why it's low (but real):* Open Graph isn't classic SEO, but a share with no title/description/image card lands flat in exactly the channels the site is engineered to spread through. This is cheap and high-leverage for share quality (SM-C4: quality of shares).
*Fix:* Specify per-route `og:title`/`og:description`/`og:image` and `twitter:card=summary_large_image` in initial HTML. The reel poster or a navy wordmark card is a natural `og:image`. Add to the SEO/GEO floor.

**L-2 · `i18n`/`hreflang` correctly out of scope — confirm no stray `lang` ambiguity.**
*Location:* `source-extraction.md` confirms i18n is not in scope (GAP noted, treated out-of-scope). Spines don't mention `lang`.
*Why it's low:* No action beyond hygiene. Single-locale is fine.
*Fix:* Just ensure `<html lang="en">` is set (trivial, but state it for the a11y/SEO overlap). No `hreflang` needed.

**L-3 · `view-source` verifiability is named as the test but no acceptance check is written into the spine for the build/QA stage.**
*Location:* SEO/GEO floor ("verifiable via `view-source` + find, JS off"); PRD FR-7 makes this a *testable consequence*.
*Why it's low:* The principle is stated; what's missing is carrying it forward as a concrete pre-launch checklist item so it's actually verified, not assumed. (The spine is the right place to *state* it; the gap is a downstream-test reminder.)
*Fix:* Add a one-line acceptance note: before launch, for each Mirror route, disable JS and confirm via `view-source` that the load-bearing facts (bio, talk titles + abstracts, project write-ups, Glass Box artifact text, the Q&A pairs from C-1, and all JSON-LD blocks) are present in the served HTML. This operationalizes NFR-3's own success criterion.

## What's solid

- **The two-layer IA is the correct backbone.** Running a crawlable Static Mirror under the cinematic arc, with the Mirror doubling as SEO substance + agent routing target + JS-off fallback, is exactly the pattern that lets an agent-first, cinematic site stay credible-when-Googled. The architecture is not the problem; the emission details are.
- **JS-off / crawlable parity is genuinely engineered, not bolted on.** Talk abstracts in native `<details>` with text in the DOM even when collapsed; bios as selectable plain text; timelines as semantic `<ol>` reflowed by CSS (DOM order preserved); the WebGL canvas `aria-hidden` with DOM equivalents; "no information lives only in the canvas/grid/ticks." This satisfies the spirit of NFR-3 for the content that *is* on the Mirror routes.
- **FR-7 / FR-8 reachability is well-honored at the navigation layer.** The static fallback footer on every page + `/browse` index reaching "100% of agent-reachable content," and the hero fork's "I'm here to book a talk" bypassing the Guide entirely to a self-sufficient `/speaking`, means the conversion path does not depend on JS or the agent — the right call for SM-C1 and for crawlers.
- **The agent is correctly framed as a router, not a silo.** "Every substantive claim carries a citation chip to a Mirror route"; below-threshold → canned answer, no model call. The design intent that no fact lives *only* in the Guide is sound; C-1 is about finishing the job (giving the Q&A itself a crawlable home), not reversing this principle.
- **Performance posture is consistent and SEO-aligned.** FCP < ~2s mobile, JS < ~200–250KB gz, ≤1 WebGL canvas lazy-loaded behind a static poster, `font-display: swap`, subset fonts, FCP-first with key content in initial HTML (SSG). Core Web Vitals and crawl-friendliness are coherent across `EXPERIENCE.md` and `DESIGN.md`.
- **Brand-string discipline is strong where it exists.** "Joshua R. Brandt, MSE" is locked as the canonical wordmark/JSON-LD string with a deliberate provenance note overriding stale mock strings ("Josh Brandt"). The remaining gap (H-2) is getting that string into an *answer sentence*, not the string itself.
- **Schema *intent* is broadly right.** Naming Person/ProfilePage, Event, VideoObject, CreativeWork, FAQPage up front shows the right GEO instinct; the findings are about surface placement, field completeness, and the two types (FAQPage, ProfilePage) that currently point at non-existent surfaces.
