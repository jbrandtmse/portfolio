# Story 2.2: Glass Box artifact reader (`/glass-box/{artifact}`)

Status: done

## Story

As a practitioner,
I want to read each published BMAD artifact as a polished long-form document,
so that I can inspect the real process behind the work, not just a summary (FR-13, UX-DR7).

## Acceptance Criteria

1. **One reader page per allowlisted artifact, in the Static Mirror.**
   **Given** the Story 2.1 render data (`web/src/generated/glassbox.json` — the `{slug,type,title,date,curatorNote,body}` set)
   **When** the dynamic route `web/src/pages/glass-box/[artifact].astro` builds via `getStaticPaths()`
   **Then** it emits one crawlable page per allowlisted artifact at `/glass-box/{slug}/` (trailing-slash form per Story 2.0 / Rule 2), each composed through `MirrorLayout` (answer-first lede leading with "Joshua R. Brandt, MSE"; self-canonical to its own absolute URL; exactly ONE `<h1>` = the artifact title; crawlable with JS off; 0 executable JS — NFR-1).

2. **The artifact-reader presents the editorial long-form (UX-DR7).**
   **Given** an allowlisted artifact's reader data
   **When** `/glass-box/{slug}/` renders
   **Then** the artifact-reader component presents, in this order: a **type chip** (the `type`, accent-outlined small-caps), the **title** (the page `<h1>`), an italic one-line **curator note** (the `curatorNote`, `--color-ink-secondary`), the artifact **date**, then the **body** rendered from markdown at the reading measure (`--measure-reading` ≈ 680px) in Source Serif — with the two long-form-only editorial devices applied: a **drop-cap** opening the first body paragraph (float left, ~3.5em, weight 700, `--color-ink-primary`, line-height ~0.78) and **pull-quotes** (body blockquotes styled italic, `clamp(20px,2.4vw,25px)`, line-height 1.4, 2–3px navy left rule). These devices appear ONLY here (the reader / case studies), never on the index or chrome.

3. **Read-only, accessible, exactly-one-h1 (UX-DR7, NFR-2, WCAG 2.1 AA).**
   **Given** the reader
   **When** audited
   **Then** it is read-only (no edit affordances/forms/buttons), uses the long-form editorial devices reserved for this surface, and meets WCAG 2.1 AA: a single `<h1>` (the title) with the artifact body's own markdown headings **demoted** (`#`→`<h2>`, `##`→`<h3>`, …) so the page keeps exactly one `<h1>` and a clean hierarchy; sufficient contrast (the tokened inks all pass AA); keyboard-operable; and any in-body links carry the global `:focus-visible` ring.

4. **Markdown is rendered safely at build time, 0-JS (NFR-1, NFR-6).**
   **Given** the artifact `body` (trusted, in-repo markdown)
   **When** it is converted to HTML
   **Then** the conversion happens at BUILD time (no client-side markdown JS; no `<script>` in the output — the page stays at 0 executable JS), the output is deterministic (same input → same HTML; NFR-6), code fences render as static `<pre><code>` (no syntax-highlight runtime), and the rendered HTML contains no executable script/inline handlers (our content is trusted prose; still assert the 0-JS floor holds on these pages).

5. **Integration AC — the reader consumes the real Story 2.1 render data (Rule 1/2).**
   **Given** the real `web/src/generated/glassbox.json` produced by `pnpm build` (Story 2.1's `render-glassbox` generator)
   **When** the site is built with the pipeline and a build-output / e2e test inspects the result
   **Then** every allowlisted artifact has a real built page at `/glass-box/{slug}/index.html` whose `<h1>` is the artifact `title`, whose first `<p>`/lede names the entity, and whose body contains real artifact prose (asserted against a known substring of a seeded artifact, e.g. the product-brief or PRD) — proving the producer→consumer wire-up end-to-end against the real generated data, not a mock.

6. **Build-ordering is robust (the forward-reference 2.1 declared).**
   **Given** that `web/src/generated/glassbox.json` is generated by `pnpm build` (pipeline) and is gitignored — so a bare `astro build` (e.g. the vitest `build-output.test.ts` `beforeAll`) on a clean checkout may not have it
   **When** the reader route builds without the generated file present
   **Then** `getStaticPaths()` degrades gracefully (no artifact present → emits zero artifact pages, never throws/crashes the build), AND any test that asserts the artifact pages exist first ensures the data is generated (runs the `render-glassbox` generator / `pnpm build`, or imports + invokes `renderGlassbox()` to write it) before building — so the Integration AC (AC5) is proven deterministically in CI, not dependent on a stale on-disk file.

## Dev Notes

### The data contract you consume (Story 2.1 — committed)

- `pnpm build` runs the `render-glassbox` generator → writes `web/src/generated/glassbox.json` = `GlassboxArtifact[]`, each `{ slug, type, title, date (ISO-8601), curatorNote, body (markdown string) }`. Seeded set today: `product-brief`, `brainstorm`, `pre-brief-research`, `prd`, `ux-design`, `ux-experience` (6). The dir is **gitignored** (regenerated each build).
- **Build-ordering (the crux — 2.1 forward-referenced this):** `pnpm build` = pipeline THEN `astro build`, so the data is present for the real build. But `web/test/build-output.test.ts` runs a BARE `astro build` in `beforeAll` (no pipeline) — on a clean CI checkout the JSON won't exist. So: (a) `getStaticPaths()` MUST tolerate absence (return `[]`); (b) any test that asserts the reader pages exist MUST generate the data first (invoke `renderGlassbox(GLASSBOX_ALLOWLIST, repoRoot)` from `scripts/render-glassbox.ts` and write the JSON, or run `pnpm build`) in its own `beforeAll`. Do NOT depend on a stale on-disk file (it happens to exist on this VM now, but CI-from-clean would fail). This is the AC6 robustness requirement.

### UX-DR7 — the reader (DESIGN.md §Typography/§Components, EXPERIENCE.md "Artifact reader")

- Reader = "header chip · curator note · **drop-cap lede** · body · pull-quote … rendered in Source Serif at a reading measure." Settled.
- **Drop-cap** (long-form only): float left, ~3.5em, line-height ~0.78, weight 700, `--color-ink-primary`; opens the first body paragraph.
- **Pull-quote** (long-form only): italic, `clamp(20px,2.4vw,25px)`, line-height 1.4, a 2–3px navy (`--color-accent`) left rule. Apply to body `<blockquote>`s.
- **Type chip**: `--color-accent`-outlined small-caps (`font-variant: small-caps`), the `type`.
- **Curator note**: italic `--font-size-body` in `--color-ink-secondary` (one line).
- **Measure**: `--measure-reading` (≈680px). Body 18px / line-height 1.62 (mobile ~17px). These devices are RESERVED for the reader (+ case studies) — never the index/chrome (DESIGN.md "Reserve drop-cap & pull-quotes for the long-form reader").
- Tokens to reuse (do not hardcode): `--color-ink-primary`, `--color-ink-secondary`, `--color-accent`, `--color-surface-raised`, `--measure-reading`, the type ramp + spacing tokens. Source Serif 4 is already self-hosted (Story 1.2).

### Critical gotcha — exactly one `<h1>` (NFR-2/SEO; existing build-output assertion)

- `MirrorLayout` emits the page's single `<h1>` (the artifact title). The artifact BODY markdown contains its OWN top-level `#` headings (e.g. the PRD body opens with `# Product Requirements…`). If rendered as-is, that becomes a SECOND `<h1>` → fails the "exactly one `<h1>`" floor + a11y hierarchy. **Demote body headings by one level** (`#`→h2, `##`→h3, …) in the markdown→HTML step. The existing `web/test/build-output.test.ts` asserts one `<h1>` per Mirror route; these new routes are Mirror routes via MirrorLayout, so they inherit that assertion.

### Markdown rendering — build-time, static, 0-JS (NFR-1)

- No markdown lib is in `web` deps yet. Add a small build-time one (`marked` or `markdown-it` — both zero-runtime-on-client when used at build) OR an Astro-native content approach. The conversion runs in `.astro` frontmatter / a build helper → static HTML in the output. MUST NOT introduce client JS (the reader stays 0 executable scripts like every Mirror route). Code fences → static `<pre><code>`; do not add a client-side highlighter. Our markdown is trusted in-repo prose, but still ensure the output carries no `<script>`/inline handlers so the NFR-1 assertions (`countExecutableScripts === 0`) hold on these pages.
- The bodies are large (PRD ≈55KB, EXPERIENCE ≈46KB markdown) → large static HTML pages. That is fine (static, crawlable, 0-JS) — it is the "read the real artifact" experience. Keep the build deterministic.

### Routing / naming (architecture §Naming, Story 2.0)

- Dynamic route file: `web/src/pages/glass-box/[artifact].astro` (bracket param syntax, architecture §Naming). Component: `web/src/components/glassbox/ArtifactReader.astro` (PascalCase). Library: `web/src/lib/glassbox.ts` (kebab). URLs are trailing-slash (`/glass-box/{slug}/`) via Story 2.0's `trailingSlash:'always'` + directory build — the canonical + any link to them must use that form (Rule 2; the form-equality test from 2.0 covers static routes — these dynamic routes follow the same convention).

### Resolved (patched in this review)

- [x] **[Review][Patch][MEDIUM] Heading renderer dropped inline markdown — 36 PRD headings shipped literal backticks.** `web/src/components/glassbox/ArtifactReader.astro` — the custom `marked` `heading` renderer returned `` `<h${demoted}>${token.text}</h${demoted}>` `` using the RAW `token.text`, so inline markdown inside a heading was emitted unparsed. Confirmed on the real built page: the PRD's 36 `#### FR-N … `[S1]`` headings shipped literal backticks (`<h5>FR-1: Calm credible hero \`[S1]\`</h5>`) instead of `<code>[S1]</code>` — an observable AC2 ("present the editorial long-form") fidelity defect on the flagship artifact. (Body paragraphs were unaffected — only the custom heading override was broken.) **Fix:** render the heading's inline tokens via `this.parser.parseInline(token.tokens)`, typed with marked's own `RendererThis` + `Tokens.Heading` (no `any`). Mirrored the fix in the vitest renderer-contract helper. Added two regression guards: a synthetic-renderer test (inline code/bold/link render inside a demoted heading) and a real-built-PRD assertion (0 literal-backtick headings; `<code>[S1]</code>` present). Verified: 0 literal-backtick headings ship; `astro check` + eslint clean; full-site build still byte-identical across two builds (NFR-6).

- [x] **[Review][Patch][LOW] Unused `slug` destructure.** `web/src/pages/glass-box/[artifact].astro:44` — `slug` was destructured from `Astro.props` but never used (TS hint). **Fix:** dropped `slug` from the destructure with a one-line comment noting the URL param is set by `getStaticPaths()`.

### Adjudicated (decision)

- [x] **[Review][Decision][ACCEPT] `marked` configured WITHOUT a sanitizer — accepted on the trusted-content boundary + the 0-JS output tripwire.** `ArtifactReader.astro` renders the body with `marked` and no HTML sanitizer, so raw `<script>` / `javascript:` URLs / `on*=` handlers in an artifact body would pass through to the rendered HTML (confirmed by the renderer-contract test, which documents this explicitly). **Decision: ACCEPT (no sanitizer added).** Rationale: the rendered content is the project's OWN allowlisted in-repo artifacts (Story 2.1 default-deny publish allowlist) — there is NO user-supplied input. The trust boundary is repo-write access + the publish allowlist, not runtime sanitization. AC4 itself states "our content is trusted prose." Defense-in-depth is provided at the OUTPUT level: QA's per-slug build-output tripwires assert the real shipped pages carry no `<script>` / `javascript:` / `on*=` (NFR-1), so a future allowlisted artifact that ever introduced executable content would FAIL the build. "Trusted-content boundary + 0-JS output tripwire" is a sufficient posture for this story. (Optional future hardening: adopt a sanitizing renderer — e.g. `marked` + a DOMPurify/`rehype-sanitize` pass — as belt-and-suspenders if the Glass Box ever admits less-trusted sources; if adopted, flip the renderer-contract test's "raw HTML passes through" expectation and update this rationale. Not required now; not deferred as a defect because the current posture is intentional and tripwire-guarded.)
