## Story

As Josh, the builder,
I want a documented path to add a new project so it appears on its own timeline,
so that the site grows by being engineered, not edited — no CMS (FR-34, UJ-4).

## Acceptance Criteria

1. **The Project Import path is documented (the three wiring points + a deterministic build).**
   **Given** a new project's curated artifacts, media, and write-up
   **When** the documented Project Import path is followed
   **Then** a committed doc (`docs/project-import.md`, linked from `content/README.md`) gives the step-by-step path that wires the project's content into the three existing source-of-truth surfaces — `content/kb/*.md` (the Guide KB markdown), the hand-curated `content/timeline/dots.ts` manifest (a Dot / flagship cluster), and `content/glassbox.allowlist.ts` (allowlist its publishable artifacts) — and a `pnpm build` regenerates the site **deterministically** (NFR-6; same repo state → byte-identical), then `scripts/deploy.sh` ships it. No file is hand-edited in `web/dist`; nothing is administered at runtime.

2. **Following the path makes the project appear on the Master Timeline + (where allowlisted) in the Glass Box.**
   **Given** the import + build
   **When** the site is rebuilt
   **Then** the project appears on the Master Timeline as a hand-curated Dot (Stage 1 — no auto-harvest) and its allowlisted artifacts are available in the Glass Box render; its `content/kb/*.md` becomes agent-retrievable once Epic 4 ships (validated there, not here). This is proven by a **mechanism test**: a sample project added to the allowlist + the timeline manifest (via the real `renderGlassbox()` / timeline render functions, against a real sample artifact file or fixture) produces the sample's Glass Box artifact + timeline Dot in the rendered output — demonstrating the path is data-driven, mechanical, and deterministic, WITHOUT polluting the live site's curated manifests.

3. **The maintenance model is a `/bmad-correct-course` engineering flow, not a CMS (FR-33).**
   **Given** the maintenance model
   **When** documented
   **Then** the path is expressed as a normal `/bmad-correct-course` (or epic/stories) → dev cycle → deploy flow — a code change, reviewed in a PR, regenerated by the build — with NO admin/CMS surface and NO runtime external reads, consistent with FR-33 (the repo is the single source of truth) and the existing `content/README.md` "code-as-CMS" framing.

4. **Integration AC — the import wiring points are real and consumed by the render pipeline.**
   **Given** the documented wiring points (`content/kb/`, `content/timeline/dots.ts`, `content/glassbox.allowlist.ts`)
   **When** the mechanism test runs against the real render functions (`scripts/render-glassbox.ts`, `scripts/render-timeline.ts` / the timeline loader)
   **Then** a sample project entry added to those data structures flows through to the rendered Glass Box artifact set + the timeline Dot set (asserted on the render output), and a second run is deterministic — proving the producer (the documented import) → consumer (the render pipeline → the live surfaces from Stories 2.2/2.3/2.4) wire-up is real, not aspirational.
